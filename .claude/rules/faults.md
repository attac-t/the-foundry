# Faults

What to do when you were wrong, and who is cheapest to hear it from.

---

## The rule

**When a person tells you something you should have seen, look back before you carry on.**

`kernel:retrospect` holds the questions and what an answer owes. This page says only when to go
there.

## Why this is a rule and not only a skill

**A skill arrives when you ask for it, and nobody asks for this one.**

`guidance.md` gives the test: would you know to go looking for it? **No means it has to already be
there**, because by the time it applies you will not know it applies.

That is exactly what happened on 20 September. The owner asked whether anything here retrospects.
**I said nothing did, and `kernel:retrospect` had shipped three weeks earlier.** I searched the
issue tracker and none of the three homes a capability lives in.

The skill was there. Nothing pointed at it.

## A repeat is the signal

One wrong call is a mistake. **The same wrong call twice is a rule nobody wrote.**

Three landed in one day and all were the same shape. A grep for a literal filename missed a loop
variable, and called four running suites orphaned. A grep for a phrase found one row of six. A
search of issues missed a skill.

**Each time the terms were the search, and each time the answer read like an absence.**

So the answer was a check and not a note. `sh bin/ships.sh <word>` now reads all three homes and
refuses to let an absence be claimed until it has answered.

## Where it lands

**Not a session note.** A learning that dies with the harness was never a learning.

A run's own record while Floor is installed. An observation when it is worth remembering, and
`kernel:craft-observation` owns that shape. A commit message otherwise.

## Nothing checks this

No exit code can tell a look back from a shrug. **This is a rule because the moment it applies is
the moment nobody feels like applying it**, which is the same reason `running.md` is one.
